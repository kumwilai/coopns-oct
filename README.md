# CoopNS-OCT, anonymous release for peer review

This repository contains the code, the data lists, the trained weights and the scripts that produce
every number and every figure in the revised manuscript. It requires no password and no account.

The archive is anonymous. Author names, institutional paths and version control history have been
removed for double blind review. A permanent citable archive will replace it on acceptance.

## What is here

    train_v8_cooperative.py                   training of the wrapper around a frozen backbone
    neuro_symbolic_corrector_v8_cooperative.py the six properties, the rule layer and the safety decision
    neuro_symbolic_corrector_v8_enhanced.py   the two correctors and the strength predictor
    neuro_symbolic_corrector_v8.py            fuzzy connectives, property definitions, verifier
    validate_crossdataset.py                  transfer to Duke17 and Duke2013 with no adaptation
    run_duke17_loo.py                         transfer with per fold adaptation
    eval_pku37_test.py                        the metric implementation used by every table
    sota/models/                              the four backbones, each about seven million parameters
    revision/                                 the study drivers, the selector, the table and figure builders
    scripts/                                  one driver per step, see MANIFEST.md
    checkpointpaper/                          weights, see checkpointpaper/README.md
    pku37_oct_dataset/, duke_sota_datasets/   the split lists, images are downloaded separately

The layout is the one the code was written for. Every script uses paths relative to this directory,
so run everything from here.

## Requirements

Python 3.10 or later with torch 2.6, numpy, scipy, scikit image, opencv and matplotlib.

    pip install torch numpy scipy scikit-image opencv-python-headless matplotlib

A GPU is not required by any script. Set DEVICE=cuda to use one. See the section on running time
before starting a full reproduction on CPU.

## Data

The three datasets are public and are not redistributed here. Download them from their authors
and place them so that the paths in the split lists resolve.

    pku37_oct_dataset/PKU37_OCT_Denoising/PKU37_OCT_Denoising/{clean,noisy}/   PKU37, Geng et al. 2022
    duke_sota_datasets/Sparsity_SDOCT_DATASET_2012/                             Duke17, Fang et al. 2012
    duke_sota_datasets/Duke2013_SBSDI/.../For synthetic experiments/           Duke2013, Fang et al. 2013

The split lists in pku37_oct_dataset/*.jsonl are the exact identity level split used in the paper,
27 clean images for training, 5 for validation and 5 for testing, giving 1388, 173 and 173 pairs.
revision/pku37_subset40.jsonl is the forty image subset used for the rule sensitivity study and
for tuning the classical operators. Run

    bash scripts/check_data.sh

to confirm every image and every weight file is present before anything else.

## Weights

See checkpointpaper/README.md. Two kinds of weights are shipped. The frozen backbones and the
correctors of the submitted version live in checkpointpaper. The correctors reported in the revised
paper are the checkpoints selected by scripts/select_config.sh and live under outputs/revision.
The submitted correctors are the warm start of every reported model, and they reproduce the
submitted tables when scored with LEGACY_SATURATING_ALLOCATION=1.

## Reproducing the paper

The fast path scores the released selected checkpoints and rebuilds every table and figure without
training anything.

    bash scripts/check_data.sh
    bash scripts/eval_in_distribution.sh
    bash scripts/eval_transfer.sh
    bash scripts/eval_studies.sh
    bash scripts/run_diagnostics.sh
    bash scripts/make_tables.sh
    bash scripts/make_figures.sh

The full path also retrains the whole search and reselects.

    bash scripts/reproduce_all.sh

Each driver skips a result file that already exists and is newer than its checkpoint, so a run can
be interrupted and resumed. Set PY to choose an interpreter, DEVICE to choose cpu or cuda, and
SEEDS, BACKBONES or CONFIGS to run part of the search. The defaults are the values used for the
paper.

## How long it takes

Measured. Scoring the 173 image test split with the NAFNet backbone took 19 seconds on the GPU
used for the paper, recorded in the field seconds of each result file. On two CPU cores the same
script scored two images in 20 seconds including model loading, so a full pass is roughly a
quarter of an hour on CPU. That figure comes from one short run and is a guide, not a benchmark.

Extrapolated. The fast path runs about thirty full passes and fifteen passes over the forty image
subset, so allow a working day on two CPU cores or under an hour on one GPU. The training search is
72 runs of ten epochs each, 4 backbones by 6 settings by 3 seeds. The paper's runs were done on one
GPU and we have not timed a full run on CPU. A single 96 by 96 crop takes a few seconds forward and
backward on two CPU cores, so a CPU reproduction of the search should be expected to take weeks
rather than hours. Anyone without a GPU should use the fast path.

## The training recipe

scripts/train_all.sh is the recipe. It is the same loop that produced the reported models, with
the interpreter, the device and the machine specific directory turned into variables. Its
properties are stated here so they cannot be missed.

Every run warm starts from the corrector of the submitted version in checkpointpaper and trains
for ten epochs with the repaired allocation rule. The backbone is frozen and its normalisation
statistics are held fixed. Every source of randomness is seeded from --seed, and each setting is
trained at seeds 0, 1 and 2.

Only two things vary between settings. The fidelity dead zone, --psnr_dead_zone, takes the values
0.3, 0.6 and 0.9 decibels. The background rule, --bg_rule, is either the intensity percentile gate
of the submitted version or a dilated Otsu tissue mask. That gives six settings per backbone.

Selection is done by scripts/select_config.sh on the validation split alone. A setting is admissible
only if it clears the bounds at its worst seed, and among admissible settings the one with the
largest lower confidence bound on its weakest clinical measure wins. The level that admitted each
backbone is recorded in outputs/revision/winners.json, including the case where no setting
qualified and the least bad one is reported. The selected checkpoints are then scored on the test
split unchanged. Nothing is retrained after selection.

## Defects found during the revision

Preparing this release meant instrumenting the code, and that exposed six defects in the version
that produced the submitted tables, the last of them after the seeded search had started. Each one is described here with what was wrong, what it
affected, how it was fixed, and how a reader can check the fix. scripts/verify_fixes.sh runs the
checks. We would rather a reviewer read this section than discover any of it alone.

### 1. The allocation map was the constant one

The fuzzy rule activations were combined so that their sum always exceeded the clamp that
followed, so the allocation map was 1.0 at every pixel of every image, the rule layer had no
effect on any output, and its parameters received no gradient. ALLOCATION_FIX.md gives the full
account, the repaired bounded formula, the proof that the clamp is now inert, and the measured
maps before and after. The original behaviour is restored exactly by LEGACY_SATURATING_ALLOCATION=1,
so the submitted numbers remain reproducible from this code.

### 2. Three loss weight flags were parsed and never used

What was wrong. train_v8_cooperative.py accepts --clinical_weight, --tci_weight and --cnr_weight.
The first and third were printed at start up and the second was never read. None of the three was
passed to the loss. The only tuned quantity that reaches the loss is --psnr_dead_zone.

What it affected. The earlier sweep ran four named settings, soft, mid, strong and max, that were
described as differing in these weights. They differed in the dead zone alone. The description of
parameter selection in the submitted paper was therefore wrong about what had been selected.

How it was fixed. The revised search varies exactly the two quantities that act, the dead zone and
the background rule, and the paper says so in Section VIII D. The three flags remain in the parser so
that the recorded commands of the submitted version still parse, and they still have no effect.

How to check. scripts/verify_fixes.sh step 1 prints every line that reads the three flags and the
line that constructs the loss.

### 3. Nothing was seeded, and the reported models were not the selected ones

What was wrong. No random generator was seeded. The earlier selector scored one run per setting,
chose the setting with the best worst clinical measure, and then trained a fresh unseeded model
with that setting, with a different batch size, and reported it. The model in the tables was never
the model that had been selected, and the spread between two runs of one setting was larger than
the spread between settings.

What it affected. Every table of the submitted version. KBNet is the visible casualty. Its selected
setting held every clinical measure positive on validation and lost two of them on test.

How it was fixed. --seed seeds Python, NumPy, torch and the data loader generator. Every setting is
trained at three seeds. revision/select_config.py admits a setting only at its worst seed and
prefers the largest lower confidence bound, and the chosen checkpoints are scored directly. The
seed to seed spread is reported beside every number in Table 3 and in Table S6 of the supplementary file.

How to check. scripts/verify_fixes.sh step 2, with RUN_SEED_CHECK=1, trains two one epoch models on
eight images with the same seed and compares every tensor. On CPU they are identical. On a GPU
cuDNN may pick different kernels between runs because deterministic algorithms are not forced, so
two GPU runs can differ at floating point precision. The paper's claim is that a setting can be
trained again and give the same model, which holds exactly on CPU and to numerical precision on
GPU.

### 4. The DnCNN backbone drifted while it was frozen

What was wrong. Freezing parameters does not stop a BatchNorm layer from updating its running mean
and variance, because they are buffers. DnCNN is the only backbone with BatchNorm, and the wrapper
was trained with model.train() and nothing else. The reference that every clinical delta is
measured against moved while the wrapper was being fitted to it.

What it affected. The DnCNN rows. On identical images the backbone's own texture contrast index
was measured at 0.550 and 0.786 across four runs.

How it was fixed. freeze_backbone_norm_stats in train_v8_cooperative.py puts every normalisation
layer of the backbone back into evaluation mode immediately after every call to model.train().

How to check. scripts/verify_fixes.sh step 3 runs revision/verify_norm_freeze.py, which passes one
batch through the backbone twice in training mode with and without the fix and prints how far the
running statistics and the output moved. With the fix both are exactly zero. We ran this on CPU.

### 5. SwinIR was trained against a different reference than it was tested on

What was wrong. To save memory the backbone outputs were cached before training. For SwinIR the
cache was built at half resolution and upsampled, so the corrector was trained against a smoothed
reference at 31.61 dB, and then tested against the tiled full resolution output at 30.00 dB, a
difference of 1.61 dB.

What it affected. The SwinIR rows, and in particular the size of its fidelity drop, which the
submitted paper attributed entirely to the backbone.

How it was fixed. The cache is now built at full resolution, see cache_ds_factor in
precompute_backbone_cache. revision/swinir_reference_check.py rebuilds both references for a set
of validation images and runs the same corrector on each, which is how the mismatch was measured.

How to check. scripts/verify_fixes.sh step 4 runs part A of that script, which reads what each
checkpoint recorded about its own cache. Part B needs the images and is faster on a GPU.

### 6. A compiled corrector was trained and an eager one was scored

What was wrong. On a GPU the training script applied torch.compile to the corrector whenever the
backbone outputs were cached, which is the case for DnCNN and SwinIR, and to the DnCNN and SwinIR
backbones when they were not cached. Every scoring script runs both eagerly. At identical resumed
weights and an identical first batch the compiled corrector reported a loss of 30.49 against 12.87
eager, and after two epochs the validation fidelity delta differed by more than a decibel. Compiling
the backbone shifted its output by up to 7.6e-3, mean 1.7e-3, against a mean correction size of
1.07e-2, so the reference that every clinical change is measured against moved by about a sixth of
the effect. The compiled percentile gate also failed at validation. There was nothing to gain, since
measured throughput was 11.2 iterations per second eager against 11.4 compiled.

What it affected. Every DnCNN and SwinIR corrector trained on a GPU before 10 September 2026 with
this script, including any run of the seeded search made before that date. NAFNet and KBNet were
never compiled and are unaffected. Runs on CPU were never compiled.

How it was fixed. Compilation is disabled on every path. The reasoning and the measurements are in
the comments of train_v8_cooperative.py at the point where compilation used to be applied. The
release contains only DnCNN and SwinIR checkpoints trained with this version of the script.

How to check. scripts/verify_fixes.sh step 6 prints the gating condition and shows that no call to
torch.compile remains on any path.

## What was tested for this release, and what was not

Tested on two CPU cores with the files in this repository. Every module imports from this
directory. Every Python file byte compiles. scripts/check_data.sh, the scoring script
revision/ablation_runner.py on two test images with the NAFNet backbone, revision/select_config.py
on the validation files of the search, and revision/verify_norm_freeze.py.

Not tested by us from this repository. The training driver, the transfer scripts, the diagnostics
pass and the figure scripts were not re run from this directory before release. They are byte
identical to the working copies that produced the paper's result files, and those were run on a
GPU. If any of them fails from a clean checkout, the fault is in this packaging and not in the
reported numbers, and we will fix it on request.

## What is not finished

Three things are honest gaps rather than finished work.

Section IX K, the cost of moving to a new backbone, has no driver. The wall clock numbers come from
the timestamps in the sweep logs and the seed spreads from the same test files as Table 3, so they
are reproducible but not regenerated by a script.

Figure S1 shows the six property maps of the submitted checkpoint, not of the selected one. The maps
are illustrative and the figure is not the source of any number, but it is not the reported model.

The matched complexity baseline under outputs/revision/matched_plain_eval.json was fitted before the
gate search that produced the selected models, so it carries the percentile gate rather than the
tissue bounded gate NAFNet was finally selected with, and its checkpoint was not kept. The paper
says this rather than claiming a match that cannot be verified from what is here.
